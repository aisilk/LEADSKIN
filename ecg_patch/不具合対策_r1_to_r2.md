## 2. 原因

r1 は、r17 で解決済みの不具合と**同じ作り方**をしていました。r17 レポート 5 章の再発防止策と照合した結果です。

| r17 の規則 | r1 の状態 | 該当する r17 の不具合 |
|---|---|---|
| 2. objc_util のメソッド呼出しは使わない（クラス作成だけ） | **違反**。BLE 開始時とアドバタイズを受けるたびに `ns()`・`ObjCInstance()`・`str(ObjCInstance)`・`ObjCClass()`・`.alloc().init()` を使っていた | No.10・11「'tuple' object is not callable」（共有の objc_msgSend の型設定が壊れる） |
| 5. BLE の操作は 1 本の作業スレッドに集める。iOS からの通知は値を取り出して渡すだけ | **違反**。CoreBluetooth の操作をメインスレッド（画面の定期処理）で行い、iPad 側は通知の中で処理・送信まで行っていた | No.14（r16 の構成。接続の瞬間に iOS の中で強制終了） |
| 4. iOS に渡したオブジェクトは自分で保持する | 一部 objc_util の参照管理（ObjCInstance の解放）に任せていた | No.12 |
| 7. スクリプトは画面を閉じるまで終わらせない | iPad 側（`patch_emu.py`）で未対応 | No.2 |
| 10. 落ちても追える仕組み | 記録はあるが fsync なし、CoreBluetooth の呼出しを記録していない | No.9 |

**落ちた場所の推定**：BLE 開始の直後は、`CBCentralManager` の作成 → 状態通知 → スキャン開始 → アドバタイズ受信と、
objc_util の呼出しが立て続けに起きます（受信 1 回ごとに `ns()` を 2 回・`ObjCInstance` を 1 回）。
r17 No.10・11 と同じく共有の objc_msgSend の型設定が壊れ、tuple のエラーの後に iOS の中で落ちたと考えられます。
iPad 側は起動しただけで接続していないため、まだ表に出ていないだけで同じ問題を持っていました（r17 No.12・14 と同じ形）。

**仕様書の問題**：仕様書 5.9 節は「CoreBluetooth の全操作をメイン（UI）スレッド」としており、r1 はこれに従っていました。
r17 の実績（No.14：メインスレッドで BLE を操作すると落ちる）と食い違うため、仕様書 5.9 節の改訂が必要です。

### 2.1 記録ファイルによる検証

| 記録から分かること | 判断 |
|---|---|
| START から **3.0 秒後**（15:33:45.128 → 48.146）に最初の異常 | BLE を始める時刻（起動 3 秒後）と一致。BLE 開始が引き金 |
| `ERR ? TypeError 'tuple' object is not callable` は作業スレッドの `pump` で発生 | `pump` はキューから取り出した関数を呼ぶだけの処理 |
| 場所が `?`＝取り出した物に `__name__` がない | その時点で r1 がキューに積むのは `mgr.start`・`on_bt_state` などのメソッドだけ（ソースで確認済み）。**積んだはずの関数が tuple に化けていた**＝Python のメモリ（オブジェクト）が壊れている |
| その後、例外の記録（`traceback.format_exc()` がソースを読む処理）の中で Segmentation fault | 壊れたメモリの上で処理を続けたため 2 次的に落ちた。落ちた場所そのものは原因ではない |
| BLE の記録が 1 行もない | r1 は CoreBluetooth の呼出しを記録していなかったため、どの呼出しの直後かは特定できない |

**結論**：r17 No.10・11 と同じ「無関係な型のエラーが不規則に出る」現象で、objc_util を実行時に使ったことによる
Objective-C 橋渡しでのメモリ破壊と判断します。2 章の見立て（規則 2・5 の違反）と矛盾しません。
r2 の対策（objc_util を実行時に使わない・BLE は作業スレッド）はこの原因を取り除く方向で、記録からは見直しの必要はありません。

## 3. 対策（r2 で実施）

| No. | 対策 | 対応する r17 の規則 |
|---|---|---|
| 1 | Objective-C の呼出しをすべて **型固定の `_send`（生のポインタ）** に統一。`ns()`・`ObjCInstance`・`ObjCClass` を実行時に使わない。文字列・配列・辞書・数値・データは `alloc/init` で作って使用後に `release` | 2 |
| 2 | objc_util を使うのは**デリゲートのクラス作成だけ**。起動時にスクリプトのスレッドで 1 回だけ行う | 2 |
| 3 | objc_runtime の関数（`sel_registerName`・`objc_getClass`・`objc_msgSend`）は**専用の型で別に作り**、objc_util が使う共有の関数の型設定に触れない | 2 |
| 4 | **BLE の操作はすべて作業スレッド**（iPhone：SessionManager と同じスレッド、iPad：模擬器の作業スレッド）。`CBCentralManager`／`CBPeripheralManager` の作成も作業スレッド | 5 |
| 5 | **デリゲートは値を取り出して作業スレッドへ渡すだけ**。iPad の読出し・書込み要求への応答、通知の送信も作業スレッドで行う | 5 |
| 6 | iPad の画面のボタン操作も作業スレッドへ渡す（画面のスレッドから模擬器の状態を直接変えない） | 5・6 |
| 7 | ペリフェラル・特性・サービス・CBUUID は **retain して閉じるまで解放しない** | 4 |
| 8 | iPad 側も `v.closed.wait()` で画面を閉じるまでスクリプトを終わらせない | 7 |
| 9 | 動作記録を **1 行ごとに fsync**。CoreBluetooth を呼ぶ直前に `CB>`、通知を受けたら `CB<`、BLE 開始の手順を `BLE-1〜3` で記録。iPad にも記録・faulthandler・前回記録の表示を追加 | 10 |
| 10 | 版を **r2** に上げ、起動中画面と iPad の画面に表示 | 10 |
| 11 | README に「Pythonista 自身のフォルダに置き、Pythonista から開く」を明記（報告の試行 1・2 はこれに当たらない置き方だった可能性あり） | 11 |

### 3.1 記録ファイルを受けた追加対策（r3）

| No. | 対策 |
|---|---|
| 12 | 例外の記録で `traceback.format_exc()` を使わず、ファイルを読まずに「ファイル名:行 関数名」だけを並べる（`safe_tb`）。メモリが壊れた後でも記録処理そのもので落ちにくくする |
| 13 | 作業キューから取り出した物が関数でなければ、呼ばずに `BAD_ITEM <型> memory corruption suspected` と記録して続ける（同じ現象が再発したら、記録で一目で分かる） |
| 14 | 例外の場所に `__qualname__`（クラス名．関数名）を記録（`?` にならない） |
| 15 | 版を **r3** に上げた（r2 から上記だけを変更） |

| ④ スレッドの組合せ | 作業スレッド・記録スレッド・画面のスレッド | r17 と同じ考え方 |

## 8. r4 診断の実機結果と対策（r5）

### 8.1 r4 の実機結果（iPhone XS・iPad Pro、2026-10-29 0:16〜0:27）

`ecg_diag_result.txt`
```
---- 00:26:27 r4 start S0
00:26:28 S0 elapsed=0  probe_ok=1  bad=0
00:26:37 S0 elapsed=10 probe_ok=47 bad=1      ← アプリのコードを使わない S0 でも破損
00:26:48 S0 elapsed=20 probe_ok=97 bad=1
---- 00:27:01 start S1      （以降、経過の行がない）
---- 00:27:10 start S2
---- 00:27:17 start S3
---- 00:27:23 start S4
```

r4 通常起動（iPhone）：`00:20:31.313 CORRUPT BAD_ITEM tuple/tuple`（起動 0.4 秒後、最初の検査で破損）→ その後 Segmentation fault。
fault の記録では、落ちた瞬間に**メインスレッドが ctypes（`ctypes/__init__.py` の `__getattr__`）の中**にいた。

iPad（patch_emu r4）：1 回目は作業スレッドの最初の ObjC 呼出し（`BLE-1 delegate alloc`、`_send`）で Segmentation fault、
2 回目は正常（Bluetooth オン・広告開始・作業スレッド動作）。

| 記録から分かること | 判断 |
|---|---|
| **S0 で破損**。S0 は標準の TextView・作業スレッド・キューと、**ui.delay で 0.2 秒ごとに予約し直す定期処理**だけで、アプリのコード・描画・ObjC・BLE を一切使わない | 原因は**アプリの処理ではなく、「ui.delay の予約を繰り返す」＋「作業スレッド」の組合せ**。本アプリ（r1〜r4）・模擬器・S0 はすべてこの方式だった |
| 落ちた瞬間、メインスレッドが ctypes の中 | 本アプリの画面の定期処理は ctypes を使わない。**ui.delay の内部（Pythonista 側）が ctypes を使っている**と考えられる |
| r17 は同じ iPhone で動く | r17 レポートの構成図は「0.2 秒ごとの **update()** で表示」（View の定期処理）で、ui.delay の繰返しではない。r17 の No.5・No.7 も ui.delay（タイマー）に関わる不具合だった |
